# Финальный pre-deployment audit NEXORA

Дата: 2026-10-09, Asia/Qyzylorda. Ветка `feature/nexora-workflow-hardening`, проверенный commit `34151f79ceac89348fed0b93fa807ccdb9c452c3`. Объединение, push, рабочие миграции и deployment не выполнялись. Приложение и опубликованные миграции в этом аудите не менялись. Новые артефакты: этот отчёт и `predeployment-demo.json`.

## Решение

**NO-GO для переключения рабочей системы сейчас.** Совместимость трёх обновлений на копии подтверждена. Это не означает, что утверждены бизнес-настройки и решён жизненный цикл ключей.

| Блокирующий пункт | Основание | Условие снятия |
|---|---|---|
| B1. Различающиеся маршруты по классификации пока нельзя надёжно включить для одного типа документа | `workflow_requirements` имеет PK только type_id; `workflows.start` выбирает правило по doc.type_id, без классификации. Разделение типов по названиям не ограничивает classification в create/PATCH | Утвердить один строгий маршрут на тип, достаточный для всех разрешённых классификаций, либо отдельно реализовать и проверить правила type+classification. Предложения ниже не объявляются уже действующими правилами |
| B2. Нет ограниченной по сроку безопасной очистки idempotency keys | Сейчас UUID произвольный, ключи/response неизменяемы и хранятся бессрочно. Удаление ключа позволит старому UUID выполнить create/upload снова | Согласовать и реализовать протокол ограниченного окна повторов с серверной проверкой возраста/эпохи, миграцией старых UUID и тестами восстановления. Для краткой локальной демонстрации можно отдельно принять бессрочное хранение; это не решение для бесконечного роста |
| B3. Не утверждён комплект реального переключения | Demo-учётные записи не являются назначенными ответственными рабочей компании; маршруты и окно переключения не утверждены. Текущая рабочая конфигурация остаётся на 0006 и старой роли | Утвердить людей/отделы/сроки, конкретные маршруты, окно, согласованный комплект API/web/Compose/секретов и production-проверки из checklist |

**GO для продолжения изолированной локальной демонстрации** в явно указанном тестовом стенде. Dev advisory не имеет обнаруженного пути из HTTP приложения и отсутствует в проверенном runtime-образе, но риск CI нужно учитывать отдельно.

## 1. Совместимость миграций и ролей

- Цепочка единственная: `0006_sessions → 0007_acl → 0008_hardening`. `alembic heads` показал `0008_hardening (head)`; `alembic check` на копии: `No new upgrade operations detected`.
- 0007 добавляет nullable снимок версии/поля привязки комментария и шесть ACL-таблиц. Старые значения не реконструируются и не переписываются. 0008 добавляет operation_keys и workflow_requirements; старые бизнес-строки не удаляются. Источники: `apps/api/migrations/versions/0007_acl.py:22`, `0008_hardening.py:12`.
- 0008 использует `nexora_immutable_row()` из более ранней миграции 0004. Установка сразу 0008 без предшествующей цепочки недопустима. Новые immutable triggers не заменяют права таблиц.
- Runtime получает SELECT/INSERT operation_keys, только SELECT workflow_requirements/acl_authorities. Голоса/квитанции/аудит не изменяет и не удаляет. Migrations владеет схемой/объектами и выполняет DDL; backup только читает таблицы и sequence. Все три — NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS; это проверено существующими тестами. Источник: `ops/database_roles.py:13`, `:40`.
- **Порядок:** закрыть запись → provision ролей/владения на существующей 0006 → миграции 0007/0008 под migrations → повторный provision точных grants новых таблиц → назначения/маршруты → API только под runtime. Provision до миграций необходим для migrations-владения, после — для runtime grants.
- `compose.roles.yaml` должен идти после остальных overlay-файлов; иначе migrate/API используют прежние подключения. API не должен запускать Alembic. `depends_on: migrate` не запускает повторное назначение grants: поэтому нельзя просто выполнить общий `up` и считать роли готовыми. Одноразовую миграцию и обновление grants завершить до старта API.
- Таблицы не принадлежат runtime/backup, эти роли не являются членами migrations. Не переименовывать рабочую БД/volumes. Повторный provision не должен случайно ротировать используемые пароли: передавать тот же согласованный набор защищённым окружением, без вывода значений.

## 4. Предлагаемые маршруты (НЕ применены к рабочим данным)

Это пример для demo, не универсальная политика компании. Точные лица и необходимость юридического этапа должны быть утверждены по типам.

| Классификация | Предложение | Доступ |
|---|---|---|
| PUBLIC | Независимый руководитель/APPROVER | Только назначенному текущему участнику; открытость документа не равна праву утверждать |
| INTERNAL | Юридическая проверка → независимый руководитель | Будущие участники не читают; версии закреплены |
| CONFIDENTIAL | Именной LEGAL → именной утверждающий | Нет автоматического доступа руководителя отдела/технического ADMIN; только текущий этап и закреплённая версия |
| RESTRICTED | Именной LEGAL → именной утверждающий; перед каждым нужным доступом отдельный временный допуск | Каждый получатель требует CUSTODIAN + SECURITY, разные люди, без самоодобрения; срок demo-допуска 1 час, максимум политики 8 часов. Истечение/отзыв закрывает файл |

Указанные этапы без условий, требуют комментария. В demo `legal` и `manager` — отдельные именованные согласующие, владелец `owner` не назначается. Их бизнес-решение не заменяет два одобрения допуска. Если этап параллельный — завершение требует всех назначенных участников; такой шаблон не обязателен для каждого документа. После решения личная квитанция, допустимый снимок без файла; допуск не переносится на новую версию. Отмена/завершение отзывает необходимость чтения, возврат на доработку требует нового запуска с новой закреплённой версией.

**Граница реализации B1:** JSON-предложение нельзя импортировать как классификационную политику в текущую workflow_requirements. Источники: `models.py:400`, `workflows.py:352`, `schemas.DocumentCreate`, `documents.update_document`. Возможен безопасный выбор без изменения кода: одна наиболее строгая утверждённая последовательность на тип для любых его классификаций. Если компании нужны разные маршруты одного типа по классификации, требуется новая реализация; пользовательское поле/название типа не является защитой от обхода.

## 5. Очистка ключей: почему обычный TTL опасен

Сейчас OperationKey имеет PK actor+UUID, hash и полный response; `idempotency.begin:16` при отсутствии записи разрешает новую операцию. UPDATE/DELETE запрещён immutable trigger (`0008_hardening.py:27`). Периодической очистки и created_at-индекса для неё нет. WorkflowEvent и FILE_UPLOAD_BLOCKED также сохраняют UUID/hash. Их нельзя чистить как временный cache: это ещё и аудит.

Измерение **только синтетического стенда**: 43 operation_keys, 90 112 bytes таблицы с индексом, средний JSON response 463 bytes. Это не прогноз рабочей нагрузки. Реальная запись может содержать больше данных. Бессрочное накопление линейно; компактные tombstone уменьшают объём, но сами остаются неограниченно растущими.

**Предложение для следующего согласования, не реализовано:**

1. Сервер выдаёт непродлеваемый подписанный retry token: actor, случайный ID, issued_at, expires_at, epoch. Клиент сохраняет его **до** отправки действия. Окно, например 30 суток, требует бизнес-утверждения; срок нельзя выставлять клиентским timestamp.
2. Сначала сервер проверяет подпись/actor/epoch/срок, затем получает actor+key lock и проверяет payload hash. Истёкший token всегда даёт 409 operation_expired, даже если строка уже удалена; никакого автоматического выполнения со старым token или выдачи нового «вместо него».
3. Серверные результаты хранить до expiry+утверждённого запаса clock skew/длительности транзакции. Очистка малыми batches, с теми же блокировками, под отдельной maintenance-ролевой процедурой, с мониторингом. Runtime не получает UPDATE/DELETE. Новый индекс/процедура/изменение trigger — отдельная новая миграция, **не правка опубликованной 0008**.
4. Старые произвольные UUIDv4 не имеют доверенного возраста: нельзя просто применять TTL. Ограничить период приёма legacy-запросов; после утверждённой даты отвергать весь legacy-протокол. Только после завершения возможных повторов можно убрать legacy operation_keys. До этого хранить/архивировать с проверкой перед исполнением; чистка старого response без минимальной записи требует адаптации API.
5. Epoch/секрет подписи хранить вне откатываемого бизнес-dump, безопасно резервировать и менять при аварийном возврате старого snapshot, чтобы запросы исчезнувших из backup операций не исполнились снова. Старый epoch отвергается; исходная система/история после точки восстановления сохраняется для сверки. Это требует процедуры и отдельного принятия недоступности автоматического retry.
6. Полный аудит WorkflowEvent/FILE_UPLOAD_BLOCKED хранить по отдельной политике компании. Не удалять историю ради очистки технического cache; дедупликация после expiry опирается на проверенный token, а не на поиск вечного cache в audit_events.
7. Добавить квоты/лимит выдачи tokens, контроль размера response и алерты по rows/bytes/oldest key. Даже 30-дневное окно не ограничивает объём при неограниченной частоте запросов.

До реализации: **не включать DELETE/TTL cleanup**, хранить ключи и включать их в backup; контролировать объём. Это безопасно от повторов, но не снимает B2. Автоматический orphan sweep файлов с grace 48 h (`app/cleanup.py`) не очищает ключи и не заменяет эту политику.

## 6. Пять high dev-зависимостей

Повторены npm audit, npm audit --omit=dev, npm ls и npm view (09.10.2026). Это **один корневой advisory** [GHSA-vfj7-8cjw-p6xm / CVE-2026-93687](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), а не пять независимых атак. Это другой дефект, не прежний CVE-2024-4068, исправленный 3.0.3.

| Пакет в lock | Почему high | Безопасное действие |
|---|---|---|
| braces 3.0.3 | Корневой stack-exhaustion advisory | Исправленного официального релиза пока нет. Не подменять библиотеку случайным fork, не считать текущую latest исправлением |
| micromatch 4.0.8 | Зависит от braces ^3.0.3 | Последняя 4.0.8 не устраняет этот новый advisory; ждать проверенного исправления upstream |
| fast-glob 3.3.1 | Зависит от micromatch | Patch 3.3.3 доступен, но всё ещё зависит от micromatch ^4.0.8 → braces. Это не исправление CVE; возможное отдельное совместимое обновление проверить в копии, не объявлять закрытием пяти high |
| @next/eslint-plugin-next 16.4.0 | Включает fast-glob 3.3.1 | Идти вместе с совместимой eslint-config-next/Next; пока latest той же цепочки не исправляет braces |
| eslint-config-next 16.4.0 | Прямая dev-зависимость, содержит plugin | npm force предлагает откат на 14.2.35, несовместимый по major с текущей линией Next 16. Не применять |

Реальная применимость: `@next/eslint-plugin-next/dist/utils/get-root-dirs.js:16` передаёт `settings.next.rootDir` в globSync. В текущем `apps/web/eslint.config.mjs` rootDir не задаётся; используется фиксированный context.cwd, а не пользовательское HTTP-поле. Отсутствие HTTP-пути подтверждается кодом и отсутствием пяти пакетов в runtime-образе `nexora-hardening-web`. Полный audit остаётся high: **не подавлять и не выдавать его за 0**.

Безопасный текущий режим: только доверенные фиксированные lint patterns/settings, ограничение времени/памяти CI; не запускать untrusted PR/config с production-секретами или привилегированным Docker socket. Это снижает применимость, не исправляет библиотеку. После официального исправления: копия frontend → точечный patch/override только с проверенными semver/registry-версиями → npm ci/audit → lint/TS/RU-EN/retry tests/build → проверка runtime trace → отдельное согласование diff lock. Установленные зависимости и lock в этом аудите не менялись.

## 8. Восстановление при ошибке

| Момент | Действие |
|---|---|
| До рабочих изменений | Не переключать; устранить причину в тестовом контуре |
| Ошибка миграции | Не продолжать автоматическое up. Проверить транзакционный rollback, revision, владельцев/grants и отпечатки; API остаётся закрыт. Provision ролей — отдельная транзакция, его состояние не откатывается автоматически вместе с Alembic |
| 0007/0008 применены, новых записей ещё нет | Проверенный на копии downgrade возможен только в окне; возврат старого широкого ACL требует отдельного принятия риска. Предпочтительно исправление вперёд |
| Уже есть полномочия, голоса, квитанции, snapshots/размеченные комментарии, ключи/route requirements | Downgrade намеренно заблокирован. Не удалять записи/не отключать triggers ради возврата; полный свежий backup и исправление вперёд |
| Нужен возврат backup | Новый кластер и новое файловое хранилище; исходные БД/uploads сохранить. Проверить manifest/dump/archive, восстановить PG, сверить файлы/sequence/связи, повторно provision ownership/grants (dump не сохраняет owner/ACL), восстановить доверенный комплект приложения/секретов/office |
| Backup старее последней записи | Сначала сверить и сохранить события после точки; не заявлять «без потери данных». Старые ключи из отсутствующих операций могут повториться. В текущем UUIDv4-протоколе безопасная отмена таких retries автоматикой не реализована: вход/запись остаются закрыты до согласованной сверки и решения |

До открытия восстановленного сервиса провести те же положительные/отрицательные API-проверки, проверку восстановления нового backup и отдельное разрешение на переключение подключения. Не восстанавливать поверх единственной исходной базы. Изолированные ресурсы аудита сохранены; их cleanup не выполнялся и не является удалением рабочих данных.
