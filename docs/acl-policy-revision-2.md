# ACL NEXORA — согласованная редакция 2

Дата: 2026-10-08. Пользователь согласовал эту редакцию как целевую политику. Реализация подготовлена и проверяется в изолированных средах; **рабочая база и рабочие контейнеры ещё используют прежнюю политику**. Пользователь разрешил commit/push после успешных проверок; внедрение в рабочую систему требует отдельного подтверждения. Результаты: [acl-implementation.md](acl-implementation.md); внедрение и откат: [acl-cutover.md](acl-cutover.md).

## Что согласовано

Будущие участники не получают доступ. После закрытия/отмены процесса доступ по его назначениям прекращается. Новые версии не наследуют старые назначения/допуски. Технический ADMIN не имеет автоматического чтения содержимого. Сервер проверяет права на каждом запросе.

Ниже согласованные правила отделового просмотра, личного снимка и временных допусков. Разрешена реализация на тестовых базах; разрешение на внедрение в рабочую систему пока не дано.

## 1. MANAGER: управленческий обзор без доступа ко всему отделу

| Состояние документа своего отдела | PUBLIC / INTERNAL | CONFIDENTIAL | RESTRICTED |
|---|---|---|---|
| DRAFT / REVISION_REQUIRED | По умолчанию скрыт. Владелец явно передаёт **конкретную текущую версию** на отделовый просмотр, если эта возможность разрешена политикой отдела | Только персональный временный допуск конкретному руководителю, выданный владельцем/уполномоченным хранителем | Только временный допуск с двумя независимыми одобрениями |
| SUBMITTED / IN_APPROVAL | По роли не открывается. Нужны активное назначение этапа или персональный допуск | То же | Активное назначение само по себе недостаточно; дополнительно два одобрения |
| APPROVED | По роли — текущая утверждённая версия, карточка и файл; не вся история | По роли нет доступа; персональный допуск | По роли нет доступа; два одобрения |
| ARCHIVED | Не считать автоматически утверждённым: архивировать можно и отменённый/отклонённый документ. Нужен явный допуск или будущая публикация утверждённой версии | Персональный допуск | Два одобрения |
| CANCELLED / REJECTED / корзина | По роли нет; корзину читает владелец. Обоснованный доступ аудитора оформляется отдельно, без обхода корзины текущей модели | То же | То же |

**Предлагаемый отделовый просмотр:** бизнес-хранитель включает возможность для отдела; владелец нажимает «Передать руководителю на просмотр», видит версию, аудиторию действующих MANAGER этого отдела и срок. Предлагаемый срок — до 7 дней. Владелец может отозвать раньше. Передача не делает материал общедоступным и не выдаёт прав правки/согласования/чтения чужих комментариев.

Разрешение действует только при ACTIVE, актуальной роли MANAGER, совпадении отдела, PUBLIC/INTERNAL, DRAFT/REVISION_REQUIRED, той же текущей версии, неистёкшем сроке и отсутствии отзыва. Новая версия, смена отдела документа/человека, повышение классификации или выход из этих состояний закрывают отделовый просмотр. Следующая версия требует новой передачи. При новом назначении руководителя аудиторию нужно пересогласовать или заново передать документ: серверная запись должна фиксировать разрешённых людей, а не автоматически расширяться на будущих руководителей. Для этой проверки модель принимает draft_share_valid как уже вычисленный сервером факт, включая членство в сохранённой аудитории, срок и отзыв; не как пользовательский флаг.

Для CONFIDENTIAL не использовать общую кнопку «всем руководителям»: только конкретные люди, версия, бизнес-цель, отдельные операции и срок (рекомендуется максимум 7 дней). MANAGER не может открыть такой документ на основании должности, самостоятельно назначить себе допуск или снизить классификацию. RESTRICTED никогда не открывается отделовым просмотром.

Пример: руководитель ИТ видит утверждённый INTERNAL регламент. Черновик записки сотрудника он не видит, пока сотрудник явно не передал v2 на просмотр. Загрузка v3 прекращает эту передачу. Конфиденциальный кадровый документ отдела остаётся закрытым до персонального допуска.

## 2. Участник после своей проверки: два разных представления

**Квитанция** доступна только самому действующему пользователю: ID назначения, ID проверенной версии, собственный результат и время. Нет актуального названия/номера, файла, чужих участников/комментариев или новых версий. Это самостоятельное минимальное подтверждение действия, не право чтения документа. Оно сохраняется после APPROVED/REJECTED/REVISION_REQUIRED/CANCELLED процесса, если человек действительно принял решение. Пользователь, чьё WAITING/PENDING просто отменили, не получает снимок проверки, которую не выполнял; можно показать отдельное минимальное сообщение об отмене его задачи без содержимого. При блокировке аккаунта квитанция недоступна. Аудит решения сохраняется независимо от видимости.

**Снимок собственной проверки** — замороженное название проверенной версии и собственный комментарий, плюс данные квитанции. Он не содержит полный файл, произвольные business_metadata, общий журнал, чужие обсуждения, последующие решения или текущую карточку. Проверка файла при работе опирается на неизменяемую версию; повторно скачать его после своего решения по старому назначению нельзя.

| После личного решения | PUBLIC / INTERNAL / CONFIDENTIAL | RESTRICTED |
|---|---|---|
| Процесс ещё RUNNING, включая следующий или параллельный этап | Квитанция + снимок до 7 дней после решения; версия только своя | Квитанция; содержимое снимка только при действующем допуске с операцией snapshot |
| Процесс завершён/отменён/возвращён/отклонён | Только квитанция; автоматическое чтение снимка прекращается | Только квитанция; прежний review-допуск прекращается |
| Прошло 7 дней, документ в корзине, доступ отозван или классификация стала RESTRICTED | Только квитанция, без содержимого снимка | Только квитанция, отдельный допуск не обходит корзину |
| Новая версия | Квитанция остаётся привязанной к прежней версии; новая карточка/файл не открываются | То же |
| Требуется расследование после закрытия | Отдельное обоснованное разрешение на сохранённый снимок, не восстановление старого назначения | Новая заявка audit_snapshot, два новых одобрения, короткий срок, только прежний снимок |

Если конфиденциальность повышена или выявлена ошибочная выдача, хранитель может немедленно закрыть снимок; при обоснованном запрете и минимальную квитанцию. Отзыв должен иметь причину и аудит. Сроки хранения личных квитанций и событий определяет компания; эти сроки отличаются от срока чтения снимка. История не удаляется при отзыве.

Сохранять снимок нужно в момент решения из закреплённого snapshot/version и собственного события. Не брать title/comment из текущего документа или комментариев по document_id. Для старых решений, где точного снимка нет, отдавать минимальную квитанцию с пометкой отсутствия снимка; не воссоздавать его из сегодняшней карточки. Все тексты интерфейса RU/EN, русский по умолчанию.

Пример: юрист завершил проверку v2, пока руководитель ещё согласует её. Юрист видит своё решение и замороженную запись собственной проверки, но не скачивает файл и не читает обсуждение руководителя. После закрытия процесса остаётся квитанция. Версия v3 никогда не появляется в этой записи.

## 3. RESTRICTED: процедура временного допуска

1. **Заявка.** Пользователь/владелец указывает получателя, документ, неизменяемую версию, необходимые операции card/file/snapshot, бизнес-цель и причину. Для snapshot без файла — только snapshot. Цель review привязана к конкретному назначению/процессу; audit_snapshot к сохранённой собственной проверке; incident к конкретной служебной необходимости. Предлагаемый срок чтения: 4 часа, максимум 8 часов. Заявка ожидает решения максимум 24 часа. Сервер проверяет полномочия заявителя, статус получателя и необходимость; браузер не задаёт роли выдающих или доверенные факты.
2. **Первое одобрение — хранитель данных.** Подтверждает бизнес-необходимость и минимальную область в пределах своих документов/отдела.
3. **Второе одобрение — уполномоченный по безопасности.** Проверяет классификацию, операции и срок. Это другой человек и другая функция. Один сотрудник с двумя полномочиями не считается двумя одобрениями. Получатель и заявитель не могут одобрять собственную заявку. ADMIN не получает ни одну функцию автоматически. Если независимых лиц нет, допуск остаётся закрытым, обхода «ради удобства» нет.
4. **Активация.** Только после двух действительных одобрений неизменённой заявки. Каждый голос связан с полным отпечатком заявки: ID, заявитель, получатель, документ, версия, операции, цель, причина, срок и крайнее время рассмотрения. Изменение любого поля аннулирует возможность использовать прежние голоса. Сервер не принимает список «одобрений» из клиента. Начало срока — время второго одобрения в UTC. Если этап будущий, допуск review ещё не активируется/не открывает документ; нужно проверять текущую необходимость, а не только наличие двух голосов.
5. **Каждый запрос.** Проверить текущие личности и области полномочий выдающих, ACTIVE получателя, совпадение документа/версии/операции/цели, состояние процесса для review, срок, отзыв, отсутствие корзины. При now >= expires_at доступ закрыт без ожидания фонового задания. Просрочка due_at задачи не заменяет срок допуска. Если допуск кончился, но задача ещё PENDING, задача остаётся в списке как «Нужен допуск», а её содержимое и решение закрываются.
6. **Истечение.** Никакого автоматического продления, переносов на новые версии или восстановления по старым голосам. Продление — новая заявка и два новых одобрения. Закрытие/отмена/возврат процесса немедленно прекращает review-допуск, даже если 4 часа ещё не прошли. audit_snapshot — отдельное основание, не перенос review-допуска.
7. **Отзыв.** Хранитель или уполномоченный по безопасности может единолично отозвать/отклонить: выдача требует двух лиц, прекращение не должно ждать второго. Сам получатель может отказаться. Отзыв, запрет, блокировка получателя/выдающего, утрата актуального полномочия, исчезновение необходимости или изменение области закрывают последующие запросы. Технический ADMIN может блокировать учётную запись по процедуре, но не создавать собственный допуск. Любое отклонение прекращает заявку; повторная выдача требует новой заявки.
8. **Аудит и гонки.** REQUESTED, ENDORSED, ACTIVATED, DENIED, EXPIRED, REVOKED и каждое чтение/скачивание — с actor, request/document/version, причиной, временем и request_id. Без паролей/полного тела документа в логах. Изменение заявки и голосование сериализуются блокировкой/ревизией, уникальным голосом одной функции и ключом идемпотентности; активация/аудит транзакционные. Времена берёт сервер. Истечение проверяется синхронно; запись EXPIRED может оформляться отложенно, но не задерживает запрет. Уже скачанную копию нельзя отозвать, начатый поток выдачи может закончиться; новые запросы после фиксации отзыва запрещены.

Пример: руководителю нужен договор RESTRICTED v2 на четыре часа. Хранитель и сотрудник безопасности отдельно одобряют доступ card/file. Только тогда руководитель видит v2. Разрешение не открывает v3 или историю. Отзыв одним из выдающих либо закрытие review-процесса прекращает доступ раньше четырёх часов. Для одной квитанции/снимка полный файл выдавать не требуется.

## 4. Исторические условия совместимости до реализации

**Этот раздел фиксирует исследование до реализации**, включая тогдашние номера строк и обнаруженные блокеры. Перечисленная адаптация теперь подготовлена; актуальные HTTP/браузерные проверки и ограничения описаны в acl-implementation.md. Формулировки «требуется» и «не реализовано» ниже относятся к историческому этапу исследования; доставка уведомлений по-прежнему отсутствует.

| Путь | Что сломается при простой замене ACL | Обязательная адаптация после согласования |
|---|---|---|
| Карточка: apps/web/src/app/(workspace)/documents/[id]/page.tsx:35–63 | Promise.all требует документ, все версии, комментарии и историю. Запрет одной ленты ломает всю загрузку | Различать полную карточку, active review, receipt; загружать только разрешённые разделы по серверным capabilities. | Решение: та же страница, mutate:75–90 | После успешного POST вызывается load полной карточки; отзыв чтения выглядит как неуспешное решение и провоцирует повтор | POST возвращает квитанцию; переходить к ней без обязательного перечитывания документа. При сетевом повторе тот же ключ возвращает свою квитанцию, без общей истории |
| Задачи: apps/web/src/app/(workspace)/approvals/page.tsx:7–17, 85–94 | Требуются title/number и Link на /documents/id даже у завершённых | Типизированные active_task/access_required/receipt/cancelled. Активная задача ведёт на /approvals/id/review; закрытая на /approvals/id/receipt; access_required на /approvals/id/access. Тексты/даты допустимы лишь в своей области; opaque ID не выдаёт доступ |
| Workflow: apps/web/src/components/workflow.tsx:27–32, 45–50, 108–119, 181–225 | Требует весь template.stages и все approvals/events; ADMIN считается владельцем | Отдавать текущий stage и разрешённые операции, собственные назначения/события; полномочия из capabilities, не role === ADMIN. Полную историю оставить владельцу/уполномоченному аудитору |
| Списки/поиск/dashboard | Могут показывать title/current_version_id и неверные totals | Единый SQL-фильтр до сортировки/пагинации; для review только замороженные необходимые поля. Минимальные квитанции отдельно от реестра документов. Избранное не сохраняет право чтения |
| Обновление статуса, отзыв, несколько вкладок | Уже загруженные данные могут остаться на экране после 403/404 | На отказ очищать содержимое/действия/локальный кэш, показывать причину без данных чужого документа; на переходах повторно проверять сервер. Отсутствие доступа не выдавать за выход из учётной записи (401) |

**Мои задачи не должны исчезать из-за истечения допуска.** Текущий этап и собственный PENDING дают человеку право видеть минимальное напоминание о его обязанности, а не содержимое документа. Поэтому RESTRICTED без допуска — безопасная строка «Нужен допуск», без названия/номера/других участников, кнопки решения и файла. Будущие WAITING не входят в список и его total. При закрытии задача уходит из pending, но реальное собственное решение остаётся в completed/rejected квитанцией. Отменённое назначение без решения отображается отдельно минимально. В этой тестовой модели проверены active_task/access_required/receipt; cancelled и пагинация нового API ещё требуют реализации/тестов.

**Уведомления сейчас не реализованы.** Это подтверждено docs/architecture.md:11, docs/workflows.md:19, отсутствием delivery/outbox обработчиков в apps/api/app и frontend. Не утверждаем, что существующая доставка протестирована. Для будущей реализации: событие нового активного назначения; перед постановкой в очередь и перед доставкой повторная проверка состояния и получателя; при истечении review-допуска безопасное напоминание о запросе допуска; после отмены/отзыва не доставлять старое «открыть документ». Текст push/email не содержит названия/файла/комментариев RESTRICTED или CONFIDENTIAL — лучше всегда нейтральное сообщение. Ссылка не является bearer-допуском, открытие заново авторизуется. Исторические события очереди не должны восстанавливать ACL. В тестовой модели notification_view проверяет только обезличенный payload, не очередь/доставку.

**История согласований сохраняется.** Для владельца — полный процесс; участнику — его квитанции/ограниченные снимки; аудитору — отдельно разрешённый журнал; техническому ADMIN — технические события без закрытого содержимого. После отмены не удалять WorkflowEvent/Approval/версии. Повтор собственного решения должен искать собственное событие до проверки чтения всего документа и возвращать тот же минимальный ответ, а чужой ключ/событие — отказ. Это важный блокер: workflows.py:394–408 сейчас вызывает get_document до previous. Изменение API потребуется отдельно.

## 5. Реализация и границы доказательств

Серверные допуски, каталог бизнес-полномочий, квитанции, новая матрица и адаптация интерфейса подготовлены. Последний полный изолированный прогон: **507 PASS, 0 XFAIL**, прежние 23 ожидаемые ошибки теперь обычные успешные регрессионные тесты. Проверены синтетическая копия старой схемы с историей согласования, обратная миграция без новых ACL-записей, блокирование опасного отката и точное восстановление 23 таблиц.

Исполняемая модель `tests/acl_candidate.py` остаётся тестовой спецификацией и не импортируется приложением. Реальный сервер реализует эти правила самостоятельно в `app/policy.py`, `app/access.py`, `app/documents.py`, `app/workflows.py`. Результаты HTTP и браузера RU/EN, ограничения и области проверки изложены в [acl-implementation.md](acl-implementation.md).

Исторический этап предложения имел 214 PASS и 23 XFAIL. Этот результат более не описывает текущий код и не используется как доказательство внедрённых запретов.

## 6. Что необходимо перед рабочим внедрением

Сама политика согласована. Ещё нужны отдельное разрешение на рабочее внедрение, утверждённые реальные хранители/ответственные за безопасность и сроки их полномочий, окно обслуживания, актуальная восстановленная копия БД **и файлов**, проверка её совместимости, переключение на минимальные роли БД. Commit/push разрешены пользователем после успешных проверок; это не разрешение на рабочее внедрение. Пошаговый порядок и откат: [acl-cutover.md](acl-cutover.md).
