# ACL Revision 2: реализация и проверка

Дата: 2026-10-09. Реализация подготовлена к публикации в main по отдельному разрешению пользователя; публикация не означает рабочее внедрение. Рабочая база не мигрировалась, рабочие контейнеры не перезапускались. Новые тестовые базы находятся в отдельных Docker-сетях, используют `nexora_test` и отдельные runtime/migrations/backup роли без SUPERUSER. Примеры и файлы стенда синтетические.

## Что реализовано

| Область | Фактическое поведение | Код |
|---|---|---|
| Серверная авторизация | Один SQL-предикат для карточки, коллекций и конкретной версии; проверка ACTIVE, цели, срока, текущих полномочий и отзыва | `apps/api/app/policy.py`: `resource_visibility`, `grant_conditions`, `active_assignment` |
| MANAGER | Автоматически только текущие APPROVED PUBLIC/INTERNAL своего отдела. Черновик скрыт до разрешения хранителя и передачи владельцем конкретным текущим руководителям; новые руководители/версии не наследуют передачу | `policy.py`: `manager_read`; `access.py`: `share_draft`, `review_policy` |
| ADMIN | Нет автоматического доступа к чужому содержимому; технические операции сохранены. Бизнес-полномочия назначает отдельный оператор БД | `policy.py`: `PERMISSIONS`; `ops/acl_authorities.py`; `ops/database_roles.py` |
| Персональный допуск | Получатель, версия, операции, цель, причина, срок и классификация фиксируются. Отзыв и истечение закрывают чтение при следующем запросе | `access.py`: `prepare_grant`, `endorse`, `revoke`; `0007_acl.py` |
| RESTRICTED | По умолчанию 4 часа, максимум 8; заявка максимум 24 часа. CUSTODIAN и SECURITY — разные люди, не заявитель/получатель. Повторная или изменённая заявка не использует старые голоса | `access.py`: `EndorseInput`, `endorse`; `policy.py`: `endorsement_valid` |
| Согласование | Только PENDING текущего RUNNING этапа и закреплённая версия; будущие назначения скрыты; для RESTRICTED дополнительно действительный допуск | `workflows.py`: `my_approvals`, `review_task`, `decide` |
| После решения | Неизменяемая личная квитанция. Собственный снимок без файла; обычный снимок максимум 7 дней пока процесс идёт. Закрытие процесса убирает автоматический снимок; для RESTRICTED возможна новая заявка только на собственный снимок с двумя голосами | `access.py`: `receipt_data`; `workflows.py`: `decision_receipt` |
| Старые данные | Сохранены назначения и события; старое решение без сохранённого личного снимка даёт только минимальную квитанцию. Снимок из сегодняшних данных не выдумывается | `receipt_data`; `ops/verify_acl_compatibility.py` |
| Защита косвенных каналов | Фильтрация до пагинации; поиск и счётчики используют разрешённые замороженные поля. Версии/файлы проверяются отдельно, комментарии привязаны к версии и этапу. Полный маршрут и его история доступны владельцу | `documents.py`, `catalog.py`, `dms.py`, `workflows.py` |
| Интерфейс | «Нужен допуск», заявки/голоса/отзыв, отдельная проверка этапа и квитанция, завершённые/отменённые задачи; загрузка разделов по серверным capabilities; очистка при отказе и защита от старых ответов | `apps/web/src/app/(workspace)/access`, `approvals`, `documents/[id]` |

## Матрица чтения по умолчанию

Владелец ACTIVE читает собственный документ. Любая роль может отдельно иметь права владельца, активного участника или адресата допуска; название роли само по себе их не выдаёт.

| Пользователь | Карточка и файл | Комментарии / полная история | После собственного решения |
|---|---|---|---|
| USER / REVIEWER / APPROVER / LEGAL без назначения | Только свои документы | Только свои | Своя квитанция, если ранее участвовал |
| MANAGER своего отдела | Текущий APPROVED PUBLIC/INTERNAL; черновик только после явной передачи | Автоматически нет | Своя квитанция |
| MANAGER: CONFIDENTIAL / RESTRICTED | Только персональный допуск; для RESTRICTED два голоса | Только отдельно разрешённая операция и версия | Своя квитанция |
| Технический ADMIN | Только свои; чужие — на общих основаниях | Чужое содержимое автоматически не открывается | Своя квитанция |
| Будущий участник | Нет | Нет | Назначение не выдаёт квитанцию решения, которого не было |
| Текущий участник | Закреплённая версия; RESTRICTED требует допуска | Только комментарии собственного текущего этапа; полный маршрут закрыт | Снимок собственной проверки по условиям политики, без файла |
| Хранитель / безопасность | Полномочие выдавать голос/отзывать не открывает документ автоматически | Нет автоматического доступа | На общих основаниях |

## Ограничения и риски

1. Это ещё не внедрённая рабочая политика. Текущая рабочая БД остаётся на 0006, её прежний SUPERUSER API ещё требует отдельного переключения по подготовленному плану ролей.
2. Старые личные снимки и неразмеченные комментарии нельзя достоверно восстановить. Они сохранены для владельца, но не выдаются участнику как его новый снимок/обсуждение этапа.
3. Доставка уведомлений раньше не была реализована. Проверены списки задач и экраны, а не несуществующая система отправки уведомлений.
4. Ограничение действует на будущие серверные запросы. Уже скачанный файл отозвать у человека технически невозможно. Интерфейс перепроверяет карточку/задачу при фокусе и каждые 20 секунд; это не мгновенное удалённое стирание уже показанного текста.
5. Автоматическое истечение проверяется синхронно; событие EXPIRED записывается при просмотре списка допусков. Планировщик уведомлений/событий истечения пока отсутствует.
6. Первое бизнес-назначение хранителей/безопасности требует отдельного утверждённого списка людей, отдела, сроков и причин. ADMIN API не может назначить эти функции.
7. Отзыв личной квитанции неизменяем: нельзя затем ослабить его. Первоначальный отзыв только снимка также нельзя преобразовать в полное скрытие второй записью; нужен отдельный последующий механизм событий отзыва. Полное скрытие можно выбрать сразу.
8. Снижение RESTRICTED блокируется; отдельная процедура рассекречивания не реализована. Renewal допуска — новая заявка с новыми голосами.
9. Сервер поддерживает дополнительные явно ограниченные операции/цели; владелец в UI по умолчанию запрашивает карточку и файл, участник — review или собственный audit_snapshot. Расширенный редактор всех операций в интерфейсе не добавлялся.
10. Нагрузочные испытания на объёмах реальной компании ещё не проводились. Политика добавляет SQL-проверки и запросы к допускам; перед большим внедрением нужен отдельный замер задержек и планов SQL.
11. Переключение обратно на старый API возвращает старые широкие права. Безопасный аварийный режим — остановка пользовательского доступа и исправление вперёд, а не автоматический запуск старой политики.
