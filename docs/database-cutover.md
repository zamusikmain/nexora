# Безопасное переключение PostgreSQL — план, пока НЕ выполнен

План предназначен для существующей локальной базы `nexora`, проекта Compose `nexora` и текущих `compose.yaml` + `compose.security.yaml`. Имя базы, volume и настройки подключения не переименовываются. Публикация кода не переключает базу. Любая остановка/пересоздание API ниже требует отдельного разрешения пользователя и согласованного окна обслуживания. Контейнер PostgreSQL не останавливается и не пересоздаётся.

## 1. Подготовка и условия допуска

- Подтвердить окно обслуживания и прекращение работы пользователей, включая прямые API-запросы. Приостановить операторские backup/cleanup/scan-запуски.
- Подтвердить администраторский доступ к текущей базе и Docker. Сохранить прежние `.env`, ссылки на секреты, конфигурацию и образ API в защищённом месте вне Git. Не менять текущие POSTGRES_USER/POSTGRES_PASSWORD.
- Подготовить три разных случайных пароля длиной не менее 20 символов: runtime, migrations, backup. Хранить в менеджере секретов либо защищённом локальном окружении. Не отправлять значения в чат.
- Убедиться, что роль `nexora_migrations` не принадлежит другим приложениям и роли не существуют с чужими настройками. Проверить отсутствие других клиентов базы: отзыв PUBLIC CONNECT/TEMP может затронуть их.
- Подготовить отдельный PostgreSQL-контейнер для восстановления. `ops/verify_database_roles.ps1` создаёт такой стенд и проверяет миграции/права. Тестовый скрипт восстанавливает исходное окружение оператора в finally. Он не подключает рабочие volumes.
- Проверить Python оператора с установленным psycopg; в текущем workspace можно использовать `apps/api/.venv-win/Scripts/python.exe`. Не выполнять рабочие pytest/TRUNCATE и downgrade.

Загрузить из менеджера секретов в окружение оператора `NEXORA_ROLE_ADMIN_URL` (psycopg URL к существующей базе), `DB_RUNTIME_PASSWORD`, `DB_MIGRATIONS_PASSWORD`, `DB_BACKUP_PASSWORD`. Значения не выводить. Подготовить URL-формы:

```powershell
$env:DB_RUNTIME_PASSWORD_URLENCODED = [Uri]::EscapeDataString($env:DB_RUNTIME_PASSWORD)
$env:DB_MIGRATIONS_PASSWORD_URLENCODED = [Uri]::EscapeDataString($env:DB_MIGRATIONS_PASSWORD)
$cutoverTestDb = 'nexora-roles-db-a9594170280d' # Проверенный отдельный стенд; при его удалении создать новый.
$cutoverStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$cutoverBackup = "backups/cutover-$cutoverStamp"
$cutoverState = "backups/cutover-$cutoverStamp-state.txt"
$cutoverOwners = "backups/cutover-$cutoverStamp-owners.json"
New-Item -ItemType Directory -Force backups | Out-Null
```

В производственной среде к Compose-командам добавляется `-f compose.production.yaml` перед `-f compose.roles.yaml`, с настоящим HTTPS WEB_ORIGIN и production-секретами. Текущее локальное development-развёртывание нельзя объявлять production только из-за смены ролей.

## 2. Свежая копия и окончательная остановка записи

Текущей утилите для упаковки файлов нужен работающий API-контейнер. Поэтому сначала, после прекращения активности пользователей, сохранить состояние и backup, затем остановить API и сравнить состояние. Никаких ролей ещё не менять:

```powershell
python ops/database_state.py --save $cutoverState
python ops/backup.py backup $cutoverBackup --legacy-admin-dump
docker compose -f compose.yaml -f compose.security.yaml stop api web
python ops/database_state.py --compare $cutoverState
```

Проверять exit code каждой команды; ненулевой код останавливает процедуру. Сравнение всех таблиц после остановки доказывает, что между начальным состоянием, дампом и остановкой не было изменений записей. Файлы версий неизменяемы; cleanup на этом интервале запрещён. Если сравнение не совпало, ничего не применять: вернуть прежние API/web, устранить активные запросы и повторить в новом каталоге. Не использовать старый backup как точку отката новых данных.

## 3. Восстановление до изменения прав

```powershell
python ops/audit_backups.py $cutoverTestDb --directory $cutoverBackup --compare-state $cutoverState
```

Команда читает существующие архивы и восстанавливает дампы только в новые базы отдельного проверенного стенда. Для именно `$cutoverBackup` обязательны: совпадение manifest, успешный pg_restore, совпадение количества ссылок/файлов и размера/SHA-256 каждой версии. Нельзя продолжать по одной отметке `verified_restore` или по успешности другого исторического снимка. При любой ошибке нового снимка вернуть прежние API/web; роли не применять. Предпочтительно дополнительно проверить вход/скачивание через API восстановленной копии; рабочие API-тесты для этого не использовать.

## 4. Снимок прав и применение в одном transaction

```powershell
apps/api/.venv-win/Scripts/python.exe ops/database_roles.py --snapshot $cutoverOwners
apps/api/.venv-win/Scripts/python.exe ops/database_roles.py --apply --confirm-database nexora
```

Первый запуск только читает метаданные. Перед вторым проверить имя базы и владельцев. Скрипт не меняет записи, структуру таблиц или значение sequence. Он создаёт новые login-роли без SUPERUSER, передаёт объекты схемы migrations и выдаёт минимальные права. Ошибка/таймаут отменяют всю транзакцию. Старый администратор остаётся действующим. Не применять ALTER USER ... NOSUPERUSER к старому владельцу вместо этой процедуры.

## 5. Проверка подключений и миграций до запуска API

Проверить реальное TCP-подключение каждой новой роли и её флаги: SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS должны быть false. Runtime и backup не должны быть членами migrations или владельцами базы/схемы. Backup должен читать таблицы; runtime должен получать отказ для DDL/TRUNCATE/изменения immutable-таблиц и переключения роли. Отрицательные проверки на рабочей базе выполняются оператором только безопасными запросами без изменений; полный набор destructive-тестов остаётся на стенде.

```powershell
docker compose -f compose.yaml -f compose.security.yaml -f compose.roles.yaml config --quiet
docker compose -f compose.yaml -f compose.security.yaml -f compose.roles.yaml run --rm --no-deps migrate
apps/api/.venv-win/Scripts/python.exe ops/database_roles.py --apply --confirm-database nexora
python ops/database_state.py --compare $cutoverState
```

Для этой задачи база уже на `0006_sessions`, поэтому `upgrade head` не должен менять данные. Если revision отличается или новая миграция требует изменения данных, остановить процедуру и согласовать её отдельно. Повторная выдача прав после Alembic нужна для новых объектов; секреты не ротируются между этими шагами. Не запускать API после неуспешного migrate/grants/сравнения.

## 6. Переключение только API

```powershell
docker compose -f compose.yaml -f compose.security.yaml -f compose.roles.yaml up -d --no-deps api
docker compose -f compose.yaml -f compose.security.yaml up -d --no-deps web
```

Не выполнять общий `up --build` с изменёнными параметрами БД. Конфигурация roles не меняет сервис db; ключ backup передаётся из окружения оператора только в одноразовый pg_dump. Администраторские/migrations/backup-секреты не передаются API. Существующие PostgreSQL и ClamAV продолжают работать.

Проверить API ready, фактического current_user=nexora_runtime и false-флаги привилегий; отсутствие ошибок прав в логах. Затем проверить вход/выход/отзыв сессии, чтение чужого документа с отказом, все существующие файлы, создание тестового документа/версии, нумерацию, комментарий и полный маршрут согласования. Тестовые действия в рабочей базе допускаются только отдельно согласованными пользователем данными; они добавляют обычные события журнала, их не удалять для сокрытия проверки.

## 7. Backup после переключения и завершение

```powershell
python ops/backup.py backup "backups/post-cutover-$cutoverStamp"
python ops/audit_backups.py $cutoverTestDb --directory "backups/post-cutover-$cutoverStamp"
```

Теперь pg_dump обязан подключаться как nexora_backup по TCP; не использовать legacy flag. Проверить новый снимок полностью. После успешных проверок разрешить пользовательскую работу, зафиксировать время переключения и результаты. Сохранить исходную копию и снимок ACL в защищённом хранилище. Очистить секреты из окружения оператора после сохранения в менеджере секретов. Старый администратор остаётся аварийной операторской учётной записью и не используется API.

## Откат

До commit транзакции прав: ошибка автоматически откатывает её; вернуть прежние API/web.

После выдачи прав или переключения API: прекратить запись, остановить API/web, загрузить исходные настройки/секреты и выполнить исходный Compose без roles, только для API/web с `--no-deps`. Старый администратор имеет доступ к объектам даже после передачи владения. На rollback нельзя запускать более старую схему/код, если параллельно выполнены другие миграции. Новые login-роли и владельцев можно оставить до расследования: данные не нужно восстанавливать поверх рабочей базы.

Полный возврат владельцев/ACL возможен администратором по сохранённому JSON, отдельной проверенной транзакцией. Не выполнять DROP ROLE CASCADE, REASSIGN OWNED по всему кластеру, DROP DATABASE, down -v или restore поверх живой базы. При реальном повреждении данных восстановить проверенный backup в отдельную новую базу/хранилище, проверить файлы и API и согласовать переключение туда; сохранить повреждённую базу для расследования.

## Что требуется от пользователя

Отдельное разрешение применить роли и перезапустить API/web; согласованное окно обслуживания; подтверждение прекращения работы пользователей; три секрета в защищённом хранилище; доступ администратора/Docker и место для свежей проверенной копии. Значения паролей в чат не требуются. Пока эти условия не выполнены, рабочая база остаётся на прежней роли.
