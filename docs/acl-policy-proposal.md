Значения PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED сохраняются в модели и карточке, но **не участвуют в действующей policy.py**. responsible_id также не даёт отдельного права чтения. Роль LEGAL/REVIEWER/APPROVER сама по себе не открывает документы.

Проверка полномочий на решение сильнее проверки чтения: решить может только назначенный пользователь текущего этапа со статусом PENDING в работающем процессе; владелец/ADMIN могут отменить процесс. Проверки и блокировки находятся в workflows.py:394–471. Поэтому запретить решение будущему участнику уже получается, а запретить ему скачать документ — пока нет.

## 2. Подтверждённые проблемы

1. **P0: прежнее или будущее назначение даёт постоянное чтение.** В assigned EXISTS нет условий RUNNING, PENDING, текущего этапа, версии, отзыва или срока (policy.py:25–31). Последствия: WAITING читает до начала этапа; APPROVED читает после решения; участник закрытого процесса читает после отмены/отклонения/возврата. Это проверено и для параллельного этапа, где другой участник ещё не решил.
2. **P0: классификация не защищает содержимое.** MANAGER читает даже конфиденциальные черновики своего отдела; ADMIN читает всё без отдельной причины (policy.py:8–48). Это разрешено текущими правилами, но противоречит предлагаемой политике.
3. **P0: доступ согласующего распространяется на все версии.** WorkflowInstance фиксирует document_version_id и metadata_snapshot (workflows.py:340–376), но чтение и скачивание используют только ACL документа. Старый согласующий может читать новые файлы после возврата на доработку.
4. **P1: слишком широкие комментарии, история и маршрут.** Глобальные потоки могут содержать обсуждения других этапов, имена участников и сведения о прежних версиях. Обрезать список документов недостаточно.
5. **P1: вторичные ответы тоже раскрывают данные.** Дашборд, счётчики, избранное, прямые ссылки, сравнение, список согласований и глобальный аудит должны использовать ту же политику. Мои завершённые согласования сейчас возвращают текущие название/номер, хотя человеку может требоваться только подтверждение собственного решения.
6. **P1: корзина не отзывает прямое чтение сама по себе.** Список исключает удалённые документы по режиму, get_document этого не делает. Состояние корзины следует учитывать в новой политике на каждом пути.

Что уже защищено: неназначенный чужой пользователь получает 404; нельзя подставить версию другого документа; анонимный/заблокированный пользователь не получает файл. Файлы выдаются через API с проверками, а не открытой публичной ссылкой. Эти свойства сохраняем.

## 3. Рекомендуемые правила Least Privilege

Отказ по умолчанию. Сервер проверяет действующего пользователя, конкретный документ, операцию, версию, классификацию, этап и статус при каждом запросе. Основания независимы: завершение назначения не отменяет права владельца или действующего отдельного разрешения.

### Роли и классификация

| Основание | PUBLIC / INTERNAL | CONFIDENTIAL | RESTRICTED |
|---|---|---|---|
| ACTIVE владелец | Свои карточка, все версии, файлы, комментарии, история; чтение также в корзине | То же | То же; распространение и снижение классификации требуют хранителя данных |
| USER, REVIEWER, APPROVER, LEGAL без назначения/разрешения | Нет | Нет | Нет |
| MANAGER своего отдела | APPROVED текущая версия; DRAFT/REVISION_REQUIRED только явно переданная на просмотр версия при включённом отделовом просмотре | Только активное назначение либо персональное разрешение, без автоматического отделового чтения | Временный допуск с двумя независимыми одобрениями |
| MANAGER другого отдела | Только отдельное назначение/разрешение | То же | Повышенный контроль |
| ADMIN как техническая роль | Нет автоматического чтения содержимого; управление системой отдельно | Нет автоматического чтения | Нет автоматического чтения |
| Активный согласующий | Снимок карточки и закреплённая версия текущего этапа | То же, назначение должно иметь обоснованную бизнес-цель | Одного назначения недостаточно: требуется разрешение хранителя данных и второго уполномоченного лица |
| Пользователь с отдельным разрешением | Только перечисленные операции и версии, до указанного срока | То же, с причиной | То же, два независимых одобрения |
| Анонимный / BLOCKED | Нет | Нет | Нет |

PUBLIC не означает публикацию в интернете или доступ всем сотрудникам. Если нужна общая библиотека, добавляем отдельное явное действие публикации утверждённой версии для выбранной аудитории. В этом предложении метка сама по себе ничего не расшаривает.

ARCHIVED не считается доказательством публикации: архивировать можно и CANCELLED/REJECTED (documents.py:213–246). Для автоматического чтения архивных материалов руководителем потребуется отдельный признак утверждённой опубликованной версии, либо явный допуск. Срок действия самого документа и срок задачи не являются сроком разрешения на чтение.

ADMIN может обслуживать пользователей/настройки без доступа к телу документов. Роль хранителя данных/делового администратора должна быть отдельной, с ограниченной областью, а не скрытым обходом ACL. Аварийное чтение техническим ADMIN — только отдельное срочное разрешение на документ, версию и операцию, с причиной, коротким сроком и независимым одобрением; для RESTRICTED обязательно два лица. Владелец не может единолично выдать RESTRICTED постороннему или снизить уровень. Нужны организационно назначенные хранители; существующая роль ADMIN этого не заменяет.

Управление пользователями остаётся сильным полномочием: технический администратор не должен самостоятельно назначать себе хранителя данных, согласующего RESTRICTED или сбрасывать чужой пароль для обхода запрета. Привилегированные назначения/восстановление доступа требуют отдельного согласования и аудита. Администраторы БД/хранилища и резервные копии — отдельная граница доверия: ACL приложения не защищает от прямого операционного доступа; нужны раздельные учётные записи, шифрование и контроль операторов.

### Состояния согласования

| Состояние человека/процесса | Доступ от назначения |
|---|---|
| Будущий этап, WAITING | Нет карточки, названия, номера, файлов, общего списка и истории |
| RUNNING + текущий этап + собственное PENDING + документ IN_APPROVAL | Только immutable снимок и document_version_id данного процесса; RESTRICTED дополнительно требует допуск |
| Срок задачи просрочен, но назначение всё ещё PENDING | Доступ сохраняется: просрочка сама по себе не завершает рабочую необходимость |
| Пользователь уже принял решение, другие участники параллельного этапа ещё работают | Файлы и текущая карточка закрываются; личная квитанция и ограниченный снимок собственной проверки по редакции 2 |
| Этап завершён, начался следующий | Предыдущим остаются квитанция/ограниченный снимок; новым чтение открывается только при их PENDING |
| Процесс APPROVED, REJECTED, REVISION_REQUIRED, CANCELLED | Доступ по назначениям закрыт всем |
| Новая версия / новый процесс | Старое назначение не переносится; новый доступ только через новое активное назначение или отдельное разрешение |
| Корзина / заблокированный пользователь / отозванный допуск | Назначение не даёт чтения |

После решения остаётся квитанция: идентификатор назначения и проверенной версии, время и собственный результат. Пока процесс RUNNING, не более 7 дней после решения, для обычных и CONFIDENTIAL документов предлагается замороженный снимок названия и собственного комментария, без файлов/чужих обсуждений/новых версий. После закрытия — только минимальная квитанция. Для RESTRICTED содержимое снимка требует отдельного временного допуска. Подробнее — в редакции 2. Срок хранения квитанций/аудита требует организационного решения; отзыв чтения не удаляет историю.

### Ресурсы и действия

| Ресурс | Владелец | MANAGER по отделу | Активный согласующий | Отдельный допуск |
|---|---|---|---|---|
| Карточка | Полная | APPROVED обычный документ; явно переданный обычный черновик | Только замороженный снимок | Только явно разрешённый снимок/карточка |
| Список версий / скачивание | Все свои | Текущая APPROVED либо явно переданная текущая версия обычного черновика | Только закреплённая версия | Только перечисленные версии |
| Сравнение | Обе версии должны быть доступны | Нет автоматически: доступна одна текущая | Нет автоматически: доступна одна закреплённая | Если отдельно разрешены обе версии и compare |
| Общие старые комментарии | Да | Нет автоматически | Нет | Отдельное разрешение |
| Новое обсуждение этапа | Да | Только как участник/по допуску | Только обсуждение собственного активного этапа | По указанной области |
| Полная история и чужие этапы | Да | Нет автоматически | Нет | Отдельный аудиторский допуск |
| Собственное решение | Да | Личная квитанция | Личная квитанция | Не расширяет чтение документа |
| Правка / новая версия / запуск / отмена | Как сейчас, с проверкой состояния; RESTRICTED распространение отдельно | Роль не даёт | Назначение не даёт | Чтение не даёт права правки |

Пример: Анна создала внутреннюю записку. Борис — юрист первого этапа, Виктор — второго. Пока работает Борис, Виктор не видит даже название. Борис видит файл v2, включённый в процесс, но не v1. После решения Бориса его доступ закрывается. Если документ вернули и Анна загрузила v3, прежние участники v3 не получают. Руководитель отдела увидит обычную текущую записку после APPROVED. Договор CONFIDENTIAL он увидит только по конкретному назначению или допуску. Технический ADMIN сможет обслужить систему, но не скачать договор без отдельного разрешения.

## 4. Как готовить исправление после согласования

1. Предварительно согласованы запрет будущих этапов, отзыв после закрытия/отмены, отсутствие наследования новых версий, отсутствие all_read технического ADMIN и проверки каждого запроса. Дополнительно согласовать MANAGER, личные снимки и сроки/процедуру RESTRICTED из редакции 2.
2. Добавить серверную модель разрешений с actor/document/version/actions, основанием, выдающим, сроком и отзывом; правила полномочий выдающего и запрет самоодобрения. Назначение этапа — вычисляемое временное основание, не постоянный grant.
3. Подготовить единый расчёт области чтения. SQL-фильтр списков/счётчиков и проверки отдельных ресурсов должны возвращать одинаковый результат; не оставлять старый can_read как альтернативный обход.
4. Добавить отдельное представление снимка для согласующих. Нынешний metadata_snapshot содержит title/confidentiality/business_metadata/revision, но не полную карточку; не достраивать его из изменяемых текущих полей. Выбрать и сохранить необходимый набор полей при запуске.
5. Привязать новые комментарии к process/version/stage и задать адресатов. Старые комментарии без области не считать публичными для участников; сохранить их, оставить владельцу/отдельному аудитору. Историю фильтровать по области, а не только document_id.
6. Проверять ACL на скачивание, обе стороны diff, версии, карточку, workflow, комментарии, историю, избранное, поиск, корзину, dashboard и approvals. Для запрещённого объекта — одинаковый 404; скрытые строки не входят в totals/статистику. Глобальный технический аудит не должен возвращать содержимое/названия закрытых документов.
   Доступ к шаблонам и их условиям/участникам также разделить: владельцу — только доступные для запуска шаблоны, техническому редактору — конфигурация по полномочию. Согласующему не отдавать полную конфигурацию всех чужих этапов.
7. Отдельно сохранить безопасную идемпотентность решения: повтор собственного уже принятого решения возвращает минимальную квитанцию, а не полный workflow. Текущий decide сначала вызывает get_document; простой отзыв чтения сломает повторы без этой доработки.
8. При чтении/скачивании проверять актуальный статус. Для гонки с отзывом определить момент авторизации: уже начатую выдачу невозможно отозвать задним числом; последующие запросы запрещаются после commit решения. Не кэшировать доступ между запросами. Уже скачанные копии ACL удалить у человека не сможет.
9. Проверить миграции и восстановление на копии; не удалять документы, версии, события, назначения. Не превращать все исторические назначения в постоянные grants. Составить список людей, которые потеряют доступ, и оформить только обоснованные новые допуски.
10. После отдельного разрешения пользователя внедрять постепенно: сравнение старого/нового решения без расширения выдачи, проверка отчёта расхождений, затем переключение в согласованное окно. Откат приложения/схемы подготовить на копии; возврат старого ACL вновь открывает известные проблемы и требует отдельного решения, а не автоматического fallback.

## 5. Что подготовлено и что тесты доказывают

* tests/acl_candidate.py — самостоятельная исполняемая модель предложения. Приложение её не импортирует. В редакции 2 добавлены правила двух одобрений, срока/отзыва, отделового просмотра, личного снимка и тестовые формы ответов для задач. Постоянное хранение и серверные ручки допусков ещё не созданы. Модель принимает доверенные серверные факты, а не поля браузера.
* tests/test_acl_policy_proposal.py — матрица ролей, классификаций, состояний, версий, корзины и запрета общих потоков.
* tests/test_acl_contracts.py — реальные HTTP-запросы к API: чужие документы/файлы, подмена версии, блокировка; отдельно strict XFAIL для известных отличий от предложения.
* XFAIL — воспроизведённое нарушение **предлагаемой**, пока не утверждённой политики. Это не исправленный production ACL. После внедрения эти метки нужно убрать и получить обычные проходящие тесты. strict=True обнаружит неожиданное изменение поведения.

Интеграционные проверки допускают только nexora_test. ops/verify_database_roles.ps1 создаёт новый PostgreSQL в отдельной сети, без рабочих томов и портов. API тестируется с минимальной runtime-ролью, данные полностью искусственные; исходный код монтируется read-only.
