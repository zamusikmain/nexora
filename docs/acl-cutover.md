# Безопасное внедрение ACL Revision 2

**Этот документ — план, не выполненное переключение.** Рабочие контейнеры/БД не менять до отдельного подтверждения пользователя. Не использовать `down -v`, удаление БД, volumes, массовое удаление старых назначений или force push.

## Перед разрешением на внедрение

1. Проверить конкретный diff и результаты в `acl-implementation.md`; отдельно разрешить commit/push, если они нужны. Зафиксировать и собрать неизменяемые версии API и web; не использовать случайный `latest` для отката.
2. Пользователь утверждает окно обслуживания, ответственного оператора, список CUSTODIAN/SECURITY по отделам (разные реальные люди), сроки полномочий, правила выдачи допусков и список отделов, где разрешён просмотр черновиков. По умолчанию отделовая передача выключена.
3. Подтвердить полное раздельное хранение runtime/migrations/backup секретов. ACL требует минимальных DB-привилегий; совместить внедрение с ранее подготовленным переходом ролей или завершить его первым отдельным этапом. Не стартовать API со стандартной командой, запускающей Alembic под runtime.
4. Подготовить свежий backup **БД + uploads** и проверить восстановление в отдельном кластере. Не считать один pg_dump резервной копией файлов. Сверить каждый storage_key, размер и SHA-256 с записью версии, количество пользователей/документов/версий/процессов/событий, номера и роли. Использовать `ops/backup.py`, `ops/audit_backups.py` и ранее подготовленный план роли backup. Старый `publication-role-state.txt` не является актуальной точкой: после него были вход/выход в рабочую систему.
5. На этой свежей рабочей **копии**, в отдельной сети без production volumes/портов, запустить upgrade 0007, provision новых grants, API под runtime и сценарии с существующими классификациями и процессами. Сверить исходные поля истории и файлы. Не запускать pytest TRUNCATE-fixtures на копии реальных данных: они разрешены только синтетической `nexora_test`.
6. На копии отдельно проверить откат до записи новых ACL-данных и аварийное восстановление целого backup в новый кластер. Откат схемы после первых снимков/голосов/квитанций намеренно запрещён: нельзя потерять эти записи ради downgrade.

## Порядок переключения после разрешения

1. Закрыть пользовательский доступ на время обслуживания и остановить запись API, не удаляя контейнеры/volumes. Проверить отсутствие активных операций. Снять согласованную свежую копию БД и uploads, записать контрольные отпечатки и идентификаторы образов.
2. Оператор отдельно проверяет адрес/имя рабочей БД и Alembic revision. Для migrations-транзакций установить короткий lock_timeout и разумный statement_timeout: если блокировки не получены, остановиться, а не продолжать частично. Стандартный upgrade запускается одноразовым мигратором с migrations URL из секретного окружения, `alembic upgrade 0007_acl`.
3. После успешной миграции администратор БД применяет подготовленный `ops/database_roles.py` к проверенному адресу, включая новые 6 ACL-таблиц и trigger function. Runtime: только SELECT на acl_authorities, INSERT на неизменяемые голоса/квитанции/отзывы; никаких прав выдачи бизнес-полномочий. Backup читает новые таблицы; migrations владеет схемой. Применение этой утилиты требует отдельного явного `--apply` и независимых секретов из среды.
4. До запуска пользовательского API сверить старые поля всех таблиц и контрольные суммы файлов с точкой до миграции. Не сравнивать полный JSON после добавления nullable-колонок без исключения новых полей; новые таблицы должны быть пустыми.
5. Оператор с **nexora_migrations** задаёт `NEXORA_ACL_OPERATOR_URL` через защищённую среду и сначала запускает `ops/acl_authorities.py` без `--apply` для каждого утверждённого сотрудника. Проверяет ID пользователя/отдела, office, UTC expiry и reason. Затем повторяет с `--apply`. Назначение транзакционно пишет отдельное событие аудита. Не поручать эту команду техническому ADMIN через API и не хранить секрет URL в командной истории/файле проекта.
6. Развернуть согласованные API/web образы одновременно. API получает только runtime URL, без операторского/migrations/backup секрета и без автоматического upgrade на старте. Сохранить private uploads, антивирусный режим, CSRF/session controls. Сначала открыть доступ только проверяющим.
7. Выполнить smoke-проверки: владелец сохраняет свои документы/историю; manager не видит неподелённый черновик/CONFIDENTIAL/RESTRICTED; technical ADMIN не видит чужой контент; будущая задача скрыта; текущая видит закреплённую версию; два голоса активируют RESTRICTED; отзыв/истечение закрывают файл; решение даёт квитанцию; отмена убирает снимок; новая версия не наследует допуск; RU/EN и прямые URLs работают корректно. Проверить точный production malware-scanning режим, не тестовый disabled-development.
8. Создать новый post-cutover backup БД+uploads, подтвердить чтение backup-ролью и восстановление в отдельном кластере с ACL-записями. Только после этого снять обслуживание. Записать фактические версии, результаты и ответственных.

## Условия остановки

Неверный адрес/роль БД, неполный backup, отсутствующие файлы/несовпадение SHA, изменение исторических данных, ошибка миграции/блокировка, неожиданный доступ в отрицательном сценарии, отсутствие независимых уполномоченных для RESTRICTED или неудовлетворительные задержки. При любом таком условии доступ остаётся закрытым, автоматический bypass не включается.

## Откат без потери истории

- **Ошибка миграции в транзакции:** PostgreSQL откатывает её целиком; проверить revision, старые отпечатки и файлы. Не повторять автоматически без выяснения причины.
- **0007 применена, но новых ACL-данных/снимков/размеченных комментариев ещё нет:** на копии доказан `alembic downgrade 0006_sessions`. Сделать только в закрытом обслуживании и после проверки данных. Возврат старого API потребует отдельного принятия риска прежних широких прав; безопаснее оставаться закрытым до исправления.
- **Есть новые записи:** downgrade блокируется и не удаляет их. Сохранить свежий полный backup, держать API закрытым, исправить вперёд на новой схеме. Не очищать ACL-таблицы, не отключать immutable triggers ради downgrade.
- **Восстановление старой точки необходимо:** восстановить backup в **новый** кластер, сохранив исходную рабочую базу и uploads. Отдельно сохранить все данные, появившиеся после этой точки, и согласовать их перенос/потерю; переключать подключения только после проверки восстановления и разрешения пользователя. Восстановление в старую БД поверх данных не использовать.

До применения нужны: разрешение на внедрение, окно обслуживания, утверждённые реальные независимые ответственные и сроки, проверенная актуальная копия БД+files, согласованные секреты/роли и готовность принять изменение доступа старых пользователей. Разрешение на commit/push — отдельное.
