## Назначение и бизнес-проблема

NEXORA хранит документы и версии, проводит согласование и оставляет доказательства решений. Восстановленная бизнес-потребность — уменьшить риск работы с неверной версией, потери истории и чрезмерного доступа. Реальные интервью с заказчиком, экономический эффект и внедрение в компанию не подтверждены.

|---|---|---|

| Поиск и dashboard | Implemented | ACL в SQL, offset pagination; не полнотекстовый поиск |
| Согласование | Implemented | Последовательные этапы, единогласие внутри этапа, закреплённая версия |

| Повтор запросов | Partially implemented | Ключи долговечны; автоматической очистки нет |

Основные сценарии: владелец регистрирует документ и загружает версию; запускает маршрут; текущий согласующий принимает решение; при возврате владелец правит документ и запускает новый процесс; допуск выдаётся на конкретную версию; завершивший участник получает собственную квитанцию без файла.

## Модули и границы

UI → API → PostgreSQL; API → приватные файлы и ClamAV. Бизнес-логика и ACL находятся на сервере. Операторские инструменты управляют DB-ролями, полномочиями CUSTODIAN/SECURITY, обязательными маршрутами и резервными копиями. Нет внешнего BPMN engine, ERP, Kafka, RabbitMQ, worker-процесса или ИИ-сервиса.

## TO-BE

Предложения: классификационные обязательные маршруты, безопасная архивация ключей повторов, SSO/MFA, уведомления с outbox, метрики и нагрузочное профилирование. Облачное объектное хранилище возможно после отдельного проектирования ACL и совместимости восстановления. Ни один из этих пунктов не считается реализованным.

## Ограничения

Один локальный storage volume связывает масштабирование и backup с топологией API. Проверка и хеширование файла синхронны. Система хранит версии, а не юридически значимую электронную подпись. Настройки production и фактическая схема рабочей БД в этом задании не проверяются.
