# NEXORA: Security & Reliability Hardening

Дата: 2026-10-09. Ветка `feature/nexora-workflow-hardening`, база изменений — опубликованная ACL Revision 2, `9c3aa1152548c3632cde5647f4451ef49cc8fefb`. Рабочая система остаётся на 0006; применение, push и merge не разрешены этим заданием.

## Подтверждённые дефекты и решения

| Проблема | Решение и исходники |
|---|---|
| PATCH требовал title и подставлял пустые business_metadata | `schemas.DocumentUpdate` принимает частичное тело; `documents.update_document` меняет только переданные поля и объединяет пользовательские ключи. Отсутствие ключа не удаляет данные; null разрешён только nullable-полям. Для обязательного custom field null запрещён. Пустой объект metadata ничего не очищает |
| PATCH пользователей сбрасывал отдел, папок — родителя, типов — определения полей | Отдельные частичные схемы `UserUpdate`, `FolderUpdate`, `TypeUpdate`. Неизвестные поля — 422, запретные поля не игнорируются |
| Контроль ревизии документа можно было опустить | expected_revision обязателен, блокировка строки с обновлением ORM-состояния. Для пользователей, папок и типов — обязательный expected_updated_at из GET; устаревшая запись возвращает 409. Изменение без фактических различий не создаёт повторный аудит этих связанных сущностей |
| Любой шаблон мог заменить обязательный маршрут | Операторская таблица workflow_requirements привязывает тип к точной неизменяемой версии шаблона и допустимым ролям. Runtime читает, но не назначает эту политику. Проверки в workflows.start; настройка inspect/apply в ops/workflow_requirements.py |
| Старое назначение могло сохраниться после утраты требуемой роли/отдела | workflows.decide повторно проверяет selector, независимость владельца и сохранённые допустимые роли. Новые процессы фиксируют план участников; несовпадение с ним закрывает решение |
| Повтор create/upload/restore создавал дубликаты | `idempotency.py`: actor+UUID, hash метода/пути/нормализованного тела, PostgreSQL advisory lock и неизменяемый OperationKey. Результат записывается в той же транзакции, что документ/версия/аудит |
| Один workflow key мог параллельно использоваться на разных объектах | Единая блокировка actor+key до блокировки документа. Конфликт между обычной операцией и WorkflowEvent также запрещён; существующая история решений сохраняется |
| Потеря ответа после commit провоцировала повторный upload | Повтор возвращает сохранённый результат, не создаёт новую версию/файл/аудит. При неопределённом исходе commit blob не удаляется; используется существующий операторский orphan sweep с периодом безопасности и проверкой БД |

## Явные бизнес-настройки и границы

- Обязательность не выводится автоматически из CONFIDENTIAL/RESTRICTED. Предприятие должно утвердить список типов, точные версии маршрутов и разрешённые роли. Миграция не выбирает маршрут и не переписывает старые документы.
- С миграции `0009_route_classification` (2026-11-08) требование задаётся парой «тип + классификация» (B1 из `predeployment-audit.md`). `classification='*'` действует для классификаций без собственного правила; все прежние строки стали `*`, их поведение не изменилось. При запуске сервер сначала ищет точное правило для текущей классификации документа, затем `*`. Снимок процесса фиксирует `required_route` (шаблон и сработавшая классификация). Настройка: `ops/workflow_requirements.py --classification CONFIDENTIAL ...` (по умолчанию `*`). Откат 0009 блокируется, если есть правила с конкретной классификацией.
- Маршрут выбирается по классификации на момент запуска. Чтобы понижением нельзя было выбрать более мягкий маршрут, с 2026-11-08 действует утверждённое правило: пока у документа нет файла, классификацию можно менять в обе стороны; после первой версии — только повышать (PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED). RESTRICTED не понижается никогда. Нарушение возвращает 403 `classification_change_forbidden`. Если понижение действительно нужно, создаётся новый документ — это видно в аудите.
- Настроенный обязательный маршрут содержит только безусловные этапы: нельзя отказаться от обязательной проверки, изменив metadata. Условные добровольные маршруты сохраняют прежнее поведение. Оператор отклоняет условный обязательный маршрут; сервер проверяет это снова.
- Для ненастроенного типа автоматического требования маршрута нет. Однако APPROVED достигается только через настоящий workflow; прямого перехода approve не существует. ARCHIVED — место хранения, не доказательство утверждения; отменённый/отклонённый документ можно архивировать по прежним правилам.
- Согласующие ACTIVE, независимы от владельца, соответствуют selector и настроенным ролям. Параллельный этап требует всех решений; следующий этап открывается после завершения текущего. RESTRICTED дополнительно требует действительного ACL-допуска, включая срок, отзыв и закреплённую версию.
- Во время IN_APPROVAL карточка/файл не редактируются. Решение проверяет current_version_id, состояние документа и закрепление процесса. Редактирование после возврата возможно в REVISION_REQUIRED, затем новый процесс с новой закреплённой версией. REJECTED/CANCELLED остаются терминальными: не добавлена универсальная процедура их повторного открытия.
- Новая политика маршрута применяется к новым запускам. Начатый процесс использует сохранённые правила; изменения не переписывают прежние назначения/историю. Старые процессы без нового плана используют исходный selector и ACL, без выдуманной реконструкции.

## Контракт повторных запросов

Idempotency-Key — UUID, обязателен для создания документов/версий/папок/типов/шаблонов, переходов документа, комментариев, move/trash/restore, восстановления версии и создания/одобрения допусков/передачи черновика. Workflow start/decisions/cancel сохраняют UUID в теле и неизменяемом WorkflowEvent. PUT/DELETE избранного уже идемпотентны; отзыв допуска уже терминален и не повторяет аудит. PATCH защищён обязательной ревизией, а не повторно применяет старое редактирование.

Тот же actor+key и другое содержимое/путь — 409 idempotency_conflict. У другого пользователя собственное пространство. Успешный результат фиксируется вместе с побочными эффектами; ошибка БД до commit оставляет ключ свободным, повтор повторно валидируется. Потеря подтверждения commit проверяется через сохранённый ключ, а не предположение о неудаче. При отказе проверки файла создаётся FILE_UPLOAD_BLOCKED с hash запроса и UUID; повтор одинакового отказа не дублирует аудит. Другие байты с этим UUID запрещены; повтор прежних байтов после восстановления сканера может завершиться успешно и создаёт ровно одну версию. Карантинный файл при отказе удаляется, карточка не меняется.

### Срок ключей (B2, утверждено 2026-11-08: окно 30 суток)

Ключ выдаёт сервер: `POST /api/v1/operation-keys` возвращает подписанный HMAC-SHA256 токен `nx1.<payload>.<sig>` (actor, случайный id операции, время выдачи, срок, эпоха). Клиент получает его **до** отправки действия, сохраняет и повторяет с ним. Сервер проверяет подпись, владельца, эпоху и срок **до** любого поиска: просроченный ключ или ключ прежней эпохи всегда получает 409 `operation_expired`, даже если сохранённый результат уже удалён, поэтому удалённая операция не выполнится повторно и не подменяется новым ключом. В БД хранится только внутренний UUID операции, поэтому `operation_keys`, WorkflowEvent, квитанции и аудит не меняли формат. Выдача ключа ничего не записывает в БД.

Миграция `0010_operation_key_expiry` добавляет `operation_keys.expires_at` (индекс). Строки по-прежнему нельзя изменять; удаление разрешено триггером только для ключей, истёкших более суток назад, — для любой роли. Runtime не имеет DELETE. Очистка: `python -m app.operation_key_cleanup` (dry-run) и `--apply` (по умолчанию запас 48 ч, минимум 24 ч) под migrations/owner-подключением; записывает `OPERATION_KEYS_PURGED`. WorkflowEvent и аудит не удаляются.

Переходный период: клиентские UUID-ключи принимаются до `LEGACY_OPERATION_KEYS_UNTIL`, после — 409 `operation_legacy_rejected`. Такие строки (`expires_at IS NULL`) не удаляются автоматически; их судьба решается отдельно после окончания периода. Production требует `OPERATION_KEY_SECRET` (≥32 символов, вне Git и дампов БД) и `LEGACY_OPERATION_KEYS_UNTIL`. После восстановления более старого backup увеличьте `OPERATION_KEY_EPOCH`: все ранее выданные ключи станут недействительными, и повторы операций, отсутствующих в backup, не выполнятся автоматически.

Frontend получает подписанный ключ у сервера и сохраняет его (ранее — сгенерированный UUID) в sessionStorage под hash actor/path/body; если ключ получить не удалось, действие не отправляется. Ниже «UUID» означает этот ключ. Frontend сохраняет UUID неизвестного результата в sessionStorage под hash actor/path/body, без паролей, содержимого файлов или CSRF. Для workflow этот UUID передаётся также в теле запроса; отдельные ключи компонентов в памяти заменены общим механизмом. Перелогин того же actor не меняет retry key. HTTP-результат ниже 500 завершает попытку; сетевой отказ/5xx сохраняет UUID. Новая намеренная операция после известного результата получает новый ключ. При отключённом sessionStorage остаётся защита повторов в текущей вкладке; после закрытия вкладки повтор неизвестной операции требует сохранённого клиентом UUID. Сервер не угадывает, какие два разных ключа означают одну пользовательскую операцию.

## Безопасное внедрение и откат

1. Отдельно утвердить применение и окно обслуживания. Зафиксировать API/frontend одной версии; сохранить предыдущие образы. Рабочие 0006/старый SUPERUSER ещё не переключены.
2. Закрыть запись на время переключения. Снять согласованный backup PostgreSQL **и uploads**, включая sequence; восстановить в новом изолированном кластере. Сверить строки/связи всех таблиц и SHA-256 каждой версии. Исходную базу/volumes сохранять.
3. На копии проверить порядок 0006 → 0007_acl → 0008_hardening. Одноразовый migrations-процесс, минимальные runtime/migrations/backup роли и grants новых таблиц; API получает только runtime secret и не запускает Alembic сам. Runtime не назначает workflow_requirements и не меняет operation_keys.
4. Утвердить CUSTODIAN/SECURITY по ACL-плану, сроки полномочий, обязательные типы/шаблоны/роли. `NEXORA_WORKFLOW_OPERATOR_URL` передаётся только защищённым окружением роли nexora_migrations. Сначала выполнить inspect, затем отдельно разрешённый apply. Отсутствующая настройка не подменяется случайным шаблоном.
5. Развернуть согласованные API и frontend вместе: старые клиенты без ключа/revision получают 422. Проверить обязательный маршрут, все этапы, самостоятельное согласование, последовательность/параллельность, PATCH сохранение metadata и 409, повторы с тем же/другим key, ACL/expiry/revoke, RU/EN и production-антивирусный режим.
6. Сделать post-update backup с новыми ключами и проверить восстановление. Только затем открыть пользовательскую запись. Нагрузочные испытания большого предприятия — отдельная работа; проверки этого этапа не являются сертификацией.

0008 — добавочная миграция, опубликованные 0001–0007 не изменены. До появления требований/ключей downgrade 0008 → 0007 допустим и проверяется на копии. При наличии новых записей он намеренно блокируется, чтобы не потерять защиту от повторов. Не удалять строки ради downgrade. При ошибке держать запись закрытой, сохранить свежий backup и исправлять вперёд. Если необходимо восстановление старой точки — новый кластер, сохранение исходной системы и отдельное согласование переноса данных после backup. Возврат старого API ослабляет новые ограничения, а возврат до ACL ослабляет также права чтения; автоматический откат на старую политику недопустим.
